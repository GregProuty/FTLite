### [P1] R1-F1 The born mask outlives its tick, and the scripted pair reads it before the next tick clears it, so a restored run can diverge from the uninterrupted run
`rockBorn` is only cleared at the start of `stepDuel` (`beginRockTick`). Between ticks it still marks the pieces made in the previous tick. Code that runs between ticks and reads it therefore behaves differently on a live state than on a clone or restore, which gets fresh zero masks. The scripted pair is one such reader: `scriptedInput` → `gunner` → `laserEligible` → `lineOfSight`, which skips born slots. It runs before `stepDuelTick`, so before `beginRockTick`. Say a piece born on tick T−1 lies across the crew-to-enemy line. The live run sees a clear line of sight. A run restored at T sees the piece blocking. The two runs then make a different `torpLock` decision, and the hashes diverge from there. The view's `laserSituation` (lineOfSight) has the same stale read. · duel.ts L1812 (impl.diff) `state.events = []; beginRockTick(state);` is the only clear. geometry.ts:L27 `if (state.rockBorn[k] === 1) continue;` and rocks.ts:L99 (firstBlocker) read it. scripted.ts:L269 `canLaunch(t, 0) && !(laserFull(t, 0) && laserEligible(t, 0, target))` sits inside `scriptedInput` (scripted.ts:L275), which callers run before `stepDuelTick` (tests/helpers/scriptedDuel.ts:L104-105, tests/helpers/duelAuthority.ts:L42, scripts/golden/duelOracle.ts:L222). hash.ts L1934 makes fresh masks in the clone. situationModel.ts:L56 calls lineOfSight between ticks. duelCheckpoint.test.ts (impl.diff L3292) restores at SPLIT 7195 and continues with the scripted driver; it passes only because no piece born at tick 7194 lies on that line. · Focus invariant 6 says nothing in a tick may depend on a mask left over from an earlier tick. Here the inputs the scripted driver feeds into a tick do depend on one. The continuation proof, the duel oracle and the duel gates all drive the sim through this path, so a save/restore equivalence that holds today by luck can break on any seed or tuning change, and the failure will look like a sim desync. · Also clear both masks at the end of `stepDuel`, after the outcome and before `tick++`. Then between ticks they are always zero, the same as in a clone or restore. Keep the clear at the start for the early-return path. Add a test: break a rock so that a piece lands on the crew-to-enemy line during tick T. Check that `rockBorn` is all zero after `stepDuel` returns, and that `scriptedInput(pair, d)` equals `scriptedInput(pair2, restored(d))` at T+1.

### [P2] R1-F2 Tests for three spec rules (pair once per tick, ship-rock inverse masses, static ram damage) would not catch a regression
(a) `a pair is resolved once per tick` asserts one bump and `rockDone` [1, 1]. But after the first resolution the pair is separated and moving apart (vc < 0).
