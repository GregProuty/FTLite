## Findings

### [P1] R1-F1 The born mask outlives its tick, and the scripted pair reads it before the next tick clears it, so a restored run can diverge from the uninterrupted run
`rockBorn` is only cleared at the start of `stepDuel` (`beginRockTick`). Between ticks it still marks the pieces made in the previous tick. Code that runs between ticks and reads it therefore behaves differently on a live state than on a clone or restore, which gets fresh zero masks. The scripted pair is one such reader: `scriptedInput` → `gunner` → `laserEligible` → `lineOfSight`, which skips born slots. It runs before `stepDuelTick`, so before `beginRockTick`. Say a piece born on tick T−1 lies across the crew-to-enemy line. The live run sees a clear line of sight. A run restored at T sees the piece blocking. The two runs then make a different `torpLock` decision, and the hashes diverge from there. The view's `laserSituation` (lineOfSight) has the same stale read. · duel.ts L1812 (impl.diff) `state.events = []; beginRockTick(state);` is the only clear. geometry.ts:L27 `if (state.rockBorn[k] === 1) continue;` and rocks.ts:L99 (firstBlocker) read it. scripted.ts:L269 `canLaunch(t, 0) && !(laserFull(t, 0) && laserEligible(t, 0, target))` sits inside `scriptedInput` (scripted.ts:L275), which callers run before `stepDuelTick` (tests/helpers/scriptedDuel.ts:L104-105, tests/helpers/duelAuthority.ts:L42, scripts/golden/duelOracle.ts:L222). hash.ts L1934 makes fresh masks in the clone. situationModel.ts:L56 calls lineOfSight between ticks. duelCheckpoint.test.ts (impl.diff L3292) restores at SPLIT 7195 and continues with the scripted driver; it passes only because no piece born at tick 7194 lies on that line. · Focus invariant 6 says nothing in a tick may depend on a mask left over from an earlier tick. Here the inputs the scripted driver feeds into a tick do depend on one. The continuation proof, the duel oracle and the duel gates all drive the sim through this path, so a save/restore equivalence that holds today by luck can break on any seed or tuning change, and the failure will look like a sim desync. · Also clear both masks at the end of `stepDuel`, after the outcome and before `tick++`. Then between ticks they are always zero, the same as in a clone or restore. Keep the clear at the start for the early-return path. Add a test: break a rock so that a piece lands on the crew-to-enemy line during tick T. Check that `rockBorn` is all zero after `stepDuel` returns, and that `scriptedInput(pair, d)` equals `scriptedInput(pair2, restored(d))` at T+1.

### [P2] R1-F2 Tests for three spec rules (pair once per tick, ship-rock inverse masses, static ram damage) would not catch a regression
(a) `a pair is resolved once per tick` asserts one bump and `rockDone` [1, 1]. But after the first resolution the pair is separated and moving apart (vc < 0). A second resolution would add no bump, no damage and no impulse, and `rockDone` is set either way. So deleting the `rockDone[o]` skip still passes. (b) The ship-rock momentum test uses r 30, whose mass is exactly SHIP_MASS (900). Swapping `is`/`ik` in the separation or the impulse still conserves momentum and still throws the ship west, so it passes. No test checks the ship's or the rock's velocity for unequal masses. (c) Spec §5.1 applies ram damage in all three cases, including a static rock that does not wake. The 40 u/s static ram test asserts kind, position, push-out, restitution and hull, but not the rock's hp, so dropping ram damage from case 2 passes. · tests/rockContacts.test.ts (impl.diff L3981-3988). rockContacts.ts L2361 `s.rockDone[o] === 1` skip. tests/rockShips.test.ts (impl.diff L4540-4546) `incoming(30, 200)` with `900 * rockAt(st, 100).vx`. contacts.ts L1741-1745 (is/ik). tests/rockShips.test.ts L4578-4589 has no hp assertion. contacts.ts L1753-1757 (ram damage after the case split). spec L344-346 (§9.3 'a pair is resolved once per tick'), spec L194-197 ('any of the three cases'). · These are the ordering and mass rules the spec calls risky. Each test passes with the rule removed, so a later refactor can break the rule silently. · (a) Build a three-body case where a second resolution of (a, b) would change state, for example b pinned against a static rock c so the a-b pair overlaps again after b's turn. Alternatively count `resolveRockPair` calls through an exported test hook. Assert one resolution. (b) Repeat the momentum test with r 15 (m 225) and assert both post-impulse velocities against (1 + 0.5)·vc·(1/m)/(1/ms + 1/mk). (c) In the 40 u/s static ram test, assert hp = before − (40 − 30)/40 · 2·900/(900 + r²).

### [P3] R1-F3 A missileLaunch admitted against a rock target can do something else when a laser shot earlier in the same tick breaks that rock
Admission evaluates `canLaunch` with the effective torpRock k. Inside `applyWeaponsInput`, `stepBurst`, a charge press or the auto-fire runs before the manual launch. If one of those shots breaks rock k, `vacate` sets torpRock to −1, and `canLaunch(state, i)` then tests the enemy instead. The command was reported 'applied', but either nothing launches, or a torpedo launches at the Hunter. This is most likely when the player has dropped both weapons on the same rock. · step.ts L1680-1683 (impl.diff), admission with torpRock. weapons.ts L2934 `stepBurst`, L2938 charge-press fireLaser and L2948 auto-fire all run before L2949 `if (input.missileLaunch && canLaunch(state, i))`. rockBreak.ts L2190 (`vacate` clears torpRock). spec L216-218 ('so its result matches what applyWeaponsInput then does'). · This is the one way the admission result can disagree with what the sim does, and the stated purpose of the effective torpRock rule is to rule that out. It is rare (the shot and the press have to land on the same tick), but the fallback to the enemy is a surprise. · In `applyWeaponsInput`, record whether torpRock was ≥ 0 when the tick began (after the rockLock fold). If it was, and it is now −1 because the rock broke, skip the manual launch rather than retargeting the enemy, and note in the plan's deviations that the result can still read 'applied'. Alternatively, document the case as accepted for the spike.
