## Findings

### [P2] R1-F1 Mouse aim follows the cursor over the console blocks, so using a side tool turns the ship toward it
Spec §6.2 says the runtime turns the pointer's bearing into an aim only while the pointer is over the Flight map, and sends the last value while it is over the side tools. The scene does not do this. Every frame it sends a steer toward options.pointer(), and that position is the last canvas pointer position, which is never cleared. The Stage is pointer-events:none, and Panels and Box outlines inherit that. So the canvas keeps receiving pointer moves over the Helm block, the Flight block panel and the contact window background. When the pilot moves the cursor to the throttle, a weapon card or the enemy window, the nose turns toward that tool. It then holds the bearing to the tool's edge, not the bearing the pilot had before. Plan ii Decision 12 assumed the DOM side tools block canvas events, which is true only of the Buttons and card hit areas, which set pointer-events:auto. · diff L1458-1460 (scene.ts: `if (p && Math.hypot(...) > pickRadius(...)) options.requests?.steer(headingOf(p.x - s.x, p.y - s.y))`, every frame, with no check on where the pointer is); diff L883 (input.ts position(): 'Not cleared'); src/renderer/src/ui/stage/Stage.tsx:7 (`pointerEvents: 'none'`); diff L5317 and L5328 (FlightStation's Box is `pointerEvents: 'none'` and its Panel sets none); only src/renderer/src/ui/stage/Button.tsx:60 sets 'auto'; spec L199-200; plan ii L55 (Decision 12). · On the Flight seat the throttle buttons, the TORPEDO card and the enemy-window room targeting all mean moving the mouse across the map toward the bottom-left or right-hand tools. Each time, the fighter turns toward that tool. This happens in ordinary play, and it contradicts spec §6.2's 'over the side tools it sends the last value'. · In the Flight block of scene.ts, send steer only when the pointer lies inside the map's usable area. Exclude the console rectangles the scene already reserves: STATION/Helm block, FLIGHT, the tab strip and CONTACT when the window is shown, i.e. CONSOLE_RESERVE.left, reserveRight and STATUS_RESERVE. Otherwise send nothing, so the runtime's `steer` keeps the last map bearing. Add a scene or model test: a pointer inside FLIGHT or CONTACT sends no steer.

### [P3] R1-F2 Spec §6.1's 'NO LASER' refusal flash is not implemented and no plan records the deviation
Spec §6.1 says laserLock, laserCharge and laserFrequency are answered `unavailable` and 'the refusal flash reads NO LASER'. The sim answers unavailable, but no view or runtime path ever produces NO LASER. On the gun Valkyrn's Flight seat, 1 and 3/4/5 are swallowed silently: the contact controller ignores Digit1 and the runtime skips the frequency and lock requests. So the pilot gets no feedback. · spec L182-184; no match for 'NO LASER' anywhere in src/, tests/ or the three plans; diff L775 (contactController: Digit1 on flight only when laserFit); runtime.ts:403-407 (lockTo and freqTo only when hasLaser()); step.ts diff L3686 and L3704 (unavailable is returned). · A spec behaviour is missing and nothing records the deviation. It is cosmetic, because the app never sends these commands on a gun class. · Either flash `refuse('fire', 'NO LASER')` (or a new control) when 1 or 3/4/5 is pressed on the Flight seat without a laser, or amend spec §6.1/§12 to say the keys are inert on the gun fit.

### [P3] R1-F3 A right-click while the torpedo is picked up both cancels the targeting and launches a torpedo
On the Flight seat, one right-button press on the map does two things. TargetingLine's window pointerdown listener cancels the armed aim, which is FTL's right-click cancel. The scene's `if (aim?.press) options.requests?.launch()` also queues a missileLaunch. A pilot who picks up the torpedo (2 or the card) and right-clicks to drop it fires the torpedo instead, untargeted. · diff L5436 (TargetingLine: `if (e.button === 2) actions.contact.cancelAim()`); diff L1461 (scene: right press → launch on Flight); runtime.ts:408 (`p.launch + launches > 0` → missileLaunch). · Two conventions on one button. The result surprises the pilot, and a torpedo is lost from the magazine of 4. · On the Flight seat, skip the launch when contact.aimWeapon() is non-null, so the right button cancels the pick-up. Or skip cancelAim when the station is flight. Document the choice in spec §5.1.

### [P3] R1-F4 Gun hits give no struck-room flash or ROOM HIT/OFFLINE callout in the enemy window
pushHits only reads 'laser' and 'missileEnd' events. A gun hit that raises a Hunter Room, even to OFFLINE, gets no struck-room flash and no callout. Only pushGunHits' spark, the -1 float and the shield pop appear. The Hound's laser gets both. · src/renderer/src/render/tactical/hitModel.ts:72-73 (only laser and missileEnd set ship/room); diff L2651-2658 (pushGunHits: spark, pop, -1 only); spec L23-24 (parity includes the console feel features). · This is a small parity gap in hit feedback. The Room the pilot is grinding down gives no confirmation when it goes OFFLINE. · In pushHits, treat a `gunHit` with room ≥ 0 on the enemy as a struck room. Have hitCallouts name a level change, for example by reading the target's rooms after the tick, or by adding a `level` flag to gunHit when gunRoomWear wraps.
