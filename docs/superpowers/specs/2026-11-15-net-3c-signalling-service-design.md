## Wire and limits

roomId/connectionId/attemptId/runId: random 128-bit lowercase 32 hex. Seat tokens/socket/link tickets: random 256-bit base64url 43 chars. Join code: eight case-insensitive Crockford-base32 characters, alphabet 0123456789ABCDEFGHJKMNPQRSTVWXYZ, collision checked. Persist only SHA-256 token/ticket hashes; no secrets in URLs/logs.

Opaque init <=65,536 bytes, checkpoint <=262,144; SHA-256 verified over exact bytes. Init/start JSON base64 body <=98,304. Checkpoint PUT raw octet-stream with bounded metadata headers; GET raw bytes/same metadata. Actual streamed-body cap, not Content-Length alone. Small REST body <=8,192; signalling WS text <=98,304 (escaped SDP plus envelope); parsed SDP/candidate retain RTC 65,536/4,096 and 128 candidates/attempt. Reject binary WS. Errors are fixed {error:{code,retryable,retryAfterMs?}}, never exception/provider text. Private responses no-store; no reflected credentials.

Routes: POST /v2/rooms; POST /v2/rooms/{code}/join; POST /v2/rooms/{roomId}/socket-ticket; GET /v2/rooms/{roomId}/socket Upgrade; POST /v2/rooms/{roomId}/turn; PUT/GET /v2/rooms/{roomId}/checkpoint. Reject query strings on authenticated routes. Internal initialization/Directory methods are not public routes. Existing-token join uses Authorization Bearer. Create/join replies expose only own token plus roomId/code/runId/seatId/seatGeneration/compatibility/capacity/roster. Socket-ticket returns single-use ticket, connectionId and epoch expiry after 30s. HTTP auth derives seat from token, never a claimed seat index.

First socket message within 5s is {type:'auth',ticket,connectionId}; atomically consume before any other action. At most 8 unauthenticated sockets/Room and one authenticated current socket/seat. Attachments contain IDs/generation, not tokens/tickets/TURN or mutable authority. Each event revalidates against SQLite current connection/generation; constructor restores routing via ctx.getWebSockets(). Persist auth deadline and use alarm plus per-event expiry checks. Attachments are an index, not truth.

Exact-key client messages, bounded requestId 1..MAX_SAFE_INTEGER per connection: ready{ready}; remove-seat{seatId}; start-propose{expectedRosterRevision,initBase64,initHash}; start-commit{proposalId,expectedRosterRevision}; link-request{guestSeatId}; signal{RtcSignal}; link-ready{attemptId}; lease-renew{nonce}; host-release; rehost-claim{expectedHostGeneration,nonce}; ack{sequence}. Correlated replies; sequenced server events: roster, start-proposed, started, link-issued, signal, link-state, lease, checkpoint-status, host-departed, host-changed, error. Client ACK after bounded validation/dispatch. Persist only byte-credit/sequence metadata, not secret outgoing payloads: <=64 unacknowledged messages AND 262,144 bytes/socket; overflow closes 1013. ACK <=lastSent releases only sent credit; future ACK cannot clear. No application retry queue. ## Directory allocation, quotas and expiry

Persist code mapping, room phase/expiry, reservations, HMAC-IP buckets and daily TURN count. Admission/SQL changes are synchronous transactions, no network await inside. Defaults: 5 creates/IP/minute, 20 joins/IP/minute, 100 active rooms, 1,000 TURN issuances/UTC day. Defensive metadata bounds: 1,000 stored rooms including retention, 10,000 live IP keys, 20 socket-upgrades/IP/minute. Exhaustion fails closed; no budget purchase/increase. HMAC-SHA256 with server-only IP_HASH_SALT over platform CF-Connecting-IP; ignore client forwarded headers. Controlled test IP only at runtime-test boundary. Missing salt/IP/accounting =>503 before allocation/provider. IP keys expire after 2min; daily count keeps current+previous day. Resolve unknown IDs through Directory before allocating Room stubs.

Creation reserves random room/code and initialization nonce, charging capacity before Room.initialize, then commits mapping. Reservation expiry 60s. Initialization repeats exact reserved data/hash or rejects conflict. Directory.commitRoom first calls synchronous, idempotent Room.confirmCreation(expectedEpoch), then rechecks the matching reservation before committing the public mapping. Room rejects already-fenced/expired initialization and persists confirmation plus the lobby deadline; it never calls back into Directory. Unconfirmed initialization may be fenced after60s. A confirmed Room reports live until its lobby deadline even if the Directory commit acknowledgement was lost: its mapping remains private until committed, its charge remains held, and exact retries may finish. Fully abandoned confirmed/private rooms conservatively consume capacity until lobby expiry. Release only matching nonce after Room fencing; abandoned/failed initialization cannot expose a partial room or exceed capacity. No raw secret before public commit. Lost response after commit leaves a charged idle lobby until expiry. Quotas not refunded.

Lobby expiry 30min from creation; active max 24h from start. Lost/ended retained 7days for reserved-token access, then removed. Directory bounded alarm sweeps <=1,000 rooms; Room alarm chooses earliest auth/ticket/proposal/lease/room deadline. Stored deadlines are authoritative even with delayed alarms. Phase updates idempotent/conservative: failed accounting keeps capacity charged. Reconcile stale reservations/expired records before allocation. Retained rooms count stored cap, not active cap; code lookup then permits existing-token operations only. Versioned phase/nonce checks prevent old lobby expiry from deleting an active mapping.

### Cross-object lifecycle protocol (builder resolution)

Directory owns a durable chargeEpoch (random transition nonce), generation, phase, charge flag and deadline per mapping. Room persists that epoch and a single pending activation operation. Creation uses the initial reservation epoch; start/rehost first prepare a unique operation in Room, then reserveActivation(roomId, previousEpoch, operationId, expectedGeneration, targetGeneration) in Directory BEFORE any usable lease. The Directory transaction changes epoch and charges one active slot if not already charged; an existing lobby/old lost charge is reused, never double-counted. A retained room facing a full cap gets retryable capacity refusal and remains lost with its checkpoint intact. Duplicate exact operation is idempotent; competing Room claims cannot prepare another operation while one is pending. Activation reservations expire after60s.

After reservation, Room rechecks operation/roster/phase/deadlines and commits the intended start/rehost plus generation/lease and new epoch in one SQL transaction, with activationAcknowledged=false. Directory commitActivation confirms that exact epoch/generation and changes its deadline to the recorded active deadline. Only then Room marks acknowledged and returns/broadcasts a usable grant. Ordinary renew/write/start follow-up is refused while unacknowledged. Exact retry or alarm reconciles an interrupted operation; a delayed acknowledgement beyond the original15s lease cannot produce a useful grant. No network await is inside a SQL transaction, and reconciliation handlers never call back into the other DO, avoiding cyclic RPC waits.

Directory NEVER frees a potentially live charge or removes a mapping solely from its own replicated phase/deadline. For expiry/cancellation it invokes Room.reconcileExpiry(expectedEpoch, now): that synchronous Room transaction either reports a current live lease/transition, or irrevocably fences the matching expired/pending/lost operation and returns a non-live receipt. Uninitialized expired creation returns absent. On return, Directory rechecks that its epoch still matches the queried epoch before releasing/updating/deleting. Failure/unavailability retains the charge and retries later. A concurrently changed epoch makes an old result a no-op. Room loss/release first fences its authority in SQL and sends an epoch-bound non-live update; Directory cannot apply it to a newer activation. A crash after reserve/Room commit/Directory ack is reconciled using persisted operation outcome, not blind timeout deletion. Unacknowledged expired operations are fenced before a retry can allocate a new epoch. Route lookup preserves activating mappings for authorized recovery; an uncommitted creation mapping is not public.

Required runtime tests race start with lobby expiry, lose/delay each cross-DO acknowledgement, fill all100 slots before retained rehost, race two rehosts for the last slot, and deliver old loss/expiry receipts after a newer generation. Verify no active mapping is removed, no charge is released twice, and no grant escapes before global admission/final acknowledgement. Fail-closed leaked capacity under unavailable accounting is preferable to exceeding the approved budget; bounded reconciliation restores it.

Implementation rulings: Room's persisted random operationId may also be the new chargeEpoch; Directory validates the exact operation tuple and rejects conflicts/reuse. This lets Room recognize a reservation after its response is lost. reserveActivation performs only synchronous admission and tuple checks, without initiating Room reconciliation. The initiating Room first fences/releases its prior epoch; independent Directory alarms and externally initiated route/create reconciliation reclaim stale other charges. Retained rehost may receive retryable capacity refusal until that sweep. Reconciliation-before-allocation applies the new-room path; activation must not create a Room-to-Directory-to-Room call cycle. Durable alarm/retry scheduling must make conservative false-full conditions recoverable.

Expired or cancelled prepared activations require a durable terminal barrier, not a read-only status query: a delayed reserve could otherwise arrive after a null result. Room fences locally and retains its full pending tuple until Directory.fenceActivation acknowledges that exact tuple. If Directory still has the predecessor epoch, fencing advances to the terminal operation epoch/target generation without a lease; if the exact reservation exists, it becomes terminal. Unrelated/newer operations are never overwritten. Delayed reserves of a terminal operation reject. The matching acknowledgement lets Room synchronize/burn the reserved generation and permit a fresh claim; lost acknowledgements retry idempotently from persisted accounting state. One bounded operation record suffices because advancing predecessor epochs rejects old requests. No reservation or status response alone grants authority.

## Link tickets and signalling

Accepted numbered request IDs increase per connection; correlated replies may complete out of request order while server envelope sequences increase in send order. An unrelated later request never alone cancels accepted asynchronous work. Recheck current authority and an operation-specific stamp after awaits. Pair issuance has a bounded pending stamp per guest pair; replacement or retirement supersedes it. Do not add an unbounded serialized request queue.

Only host requests host-to-guest attempt for current socket pair. Persist attemptId, host/guest-seat generations, connection IDs, ticket hashes, issued/expiry/ready bits. Distinct random tickets delivered inverted as local/expected values once to both endpoints; discard plaintext after sends. Failure cancels attempt. Replacement invalidates prior route and emits close to both. No attempt/ticket reuse. Unready expires after 30s; completed route remains bound to current identities. At most 3 live pairs and 128 retained metadata rows with expiry cleanup.

Forward original RtcSignal only if sender/from/to belong to current pair, room/generations match, host sends offer/guest answer, and byte/candidate bounds hold. The service's128 candidate messages/attempt limit is aggregate across both directions, including end markers consistently with native counting; existing per-receiver native limits remain unchanged. Reject guest-to-guest, stale/unknown/future identity routes. link-ready idempotent per endpoint; both bits mark association ready, never prove gameplay bytes to service. Existing RTC peer checks ticket/full identity/mutual hello. Provider closes transport on link-state invalidation; native service gate checks stale/replayed tickets cannot become another active link.

Builder resolution: existing RtcIdentity.seatGeneration and RtcSignal.seatGeneration mean the GUEST seat's generation on BOTH endpoints of a pair. Room separately persists/checks each sender's own seat generation through its authenticated current socket and both endpoint connection IDs. HostGeneration retains authority fencing meaning. Do not rewrite a forwarded signal or assign each endpoint its own generation. Native proof must use unequal host/guest generations, then independently replace guest and host connections and reject obsolete pairs. Room sends both link-issued events before accepting later signal forwarding; guest event precedes host event. Provider event handling synchronously invokes the existing startAttempt before later signal dispatch, preserving ordered start/signal IPC even though readiness resolves asynchronously.
