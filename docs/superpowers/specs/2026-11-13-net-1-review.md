# Review of the Net-1 Foundations Spec (Claude, 2026-11-13)

Reviewed: `docs/superpowers/specs/2026-11-13-net-1-foundations-design.md` (written by Codex), against the code at HEAD 35e2a90 and the decision record `2026-11-13-networking-decision.md`.

## Verdict

The spec is thorough and mostly right: its code references check out (for example `console.ts:104`, the offline tab that takes no input; `science.ts:94-96`, scanning reads the cursor; `productive.ts:27`; `consoleSystem` charging before input). Its command contract, ID ledger, clock rules, disposal plan and determinism guard are sound.

There is **one structural problem**: the ActionWindow rendezvous in section 5. There are also **scope and ordering issues**, and five small fixes. I recommend the changes below as amendments before planning.

## 1. Drop the ActionWindow rendezvous (major)

**What the spec does.** To keep bit-exact parity with today's controller, the authority stops inside each tick. It publishes an "interaction view" and then one "console view" per seated player, waits for every local controller to reply with commands for that phase, then continues (section 5, last two paragraphs; `ActionWindow` / `ActionWindowReply`).

**Why it is wrong for Net-1:**
- It couples the authority to its clients mid-tick, which is exactly what the network model forbids. The spec admits that Net-3 "must not wait for a remote ActionWindowReply". So Net-1 would build and test a mode that is thrown away, and Net-1 would not prove the boundary Net-3 relies on.
- It adds protocol messages, error paths (missing or double replies, late replies, a bounded loop) and a synchronous drain to every tick, all for offline play.
- The parity it protects does not need it. With **explicit commands** validated at execution, the authority already applies a command in the right phase:
  - **Charge threshold.** A Confirm pressed on the tick the Pulse finishes charging fires today, because `chargeBeam` runs before input (`console.ts:108`). The client emits `fire(weapon, target)` whenever the player presses Confirm on that row, without pre-checking readiness. The authority executes it in phase C after charging, so the outcome is the same.
  - **Cursor move plus Confirm in one tick.** The client emits `selectTarget` then `fire` with consecutive sequence numbers, applied in order in the same slot.
  - **Rows that relocate.** Each card has one occupant. The row lists (Navigation rows, Science and Weapons targets) change from director, enemy and decision steps that run *after* the console slots, not from another player's console action in the same tick. Same-tick cross-player relocation is therefore close to impossible. Any case the differential trace finds is traced, not engineered around.
  - **Same-tick seating.** "A player who sits acts from the next tick" stays an authority rule (`satThisTick`). It does not need a client view.

**Replacement.** Clients translate presses into commands for tick T from the **latest published state (end of T-1)** plus their own card UI state: one tick of decision latency, the same as any network client. The authority admits commands addressed to T and validates and executes them in their phase. This is the Net-3 model, so Net-1 proves it. Delete `ActionWindow`, `ActionWindowReply` and `windowId`.

**Bots.** Run them **beside the authority** (host-side agents) through the same translator against the same published view, with their controller memory in the authority checkpoint, as section 10 already plans. Today `botIntent` reads start-of-tick state (`sim/acceptance.ts:16` calls it before `step`), which is the same timing, so bot gates should hold.

**Parity rule.** Gate figures are unchanged, or they move only for a traced reason ("a press on tick T now resolves against the T-1 view because ..."). No floor is lowered. Expected movement is none or tiny; the differential traces in sections 11 and 12 are the check.

## 2. Split Net-1 into two milestones (scope)

Eighteen tasks with a cutover at task 17 means the boundary only goes live at the end, and a review cannot see progress.

- **Net-1a, "the boundary":**
  - baseline fixtures;
  - protocol contracts;
  - loopback;
  - the command ledger;
  - the semantic commands (tasks 6–10);
  - card UI extraction;
  - bots beside the authority;
  - the headless run owner and clock;
  - the published state and replica;
  - the couch cutover.

  Couch play runs through the authority at the end of Net-1a.
- **Net-1b, "durability":**
  - disposal and entity reuse (task 2);
  - the per-viewer HUD model (task 15);
  - replay and checkpoint v2 (task 16);
  - the cross-engine harness and AST guard (task 18).

Move disposal to Net-1b too. Net-1a's offline couch never runs a long-lived multi-run authority, while Net-3's host does. The AST Math guard is small and can land first in Net-1a as a safety net.

## 3. Smaller fixes

1. **Net-0's status line.** The owner approved Net-0 ("start the spec"). Update its status to "approved 2026-11-13" and drop the hedging sentence from Net-1's status line.
2. **Command count.** The decision record says "about 22"; the spec has 26 (24 gameplay, `setPaused`, reserved `moveTo`). That is fine. Section 5 should say why the extras exist: `selectWeapon`, `selectTarget`, `swapCargo`, `airlockToggle` and `toggleDoorLocal`.
3. **The vote command.** The current cycling behaviour (each standing press advances your vote, `run.ts:318`) is a gamepad affordance, not a semantic. Keep `vote(event, choice)` as the authority command. The client turns repeated presses into the next choice, so the authority never cycles. The spec's row is close, but it keeps "cycling" inside the authority for standing players. Make the client resolve the choice.
4. **The callout request** should be listed in the command or auxiliary message union with its validation (section 7 mentions it only in prose).
5. **The 120-tick catch-up cap per pump.** State what happens past about 2 s of debt, a value up to the spec: keep catching up across pumps, with the catching-up state shown, so long stalls never silently drop time. The text implies this; make it explicit in the tests.

## 4. What is already right (keep)

- The closed message unions, runtime validation, and command IDs per (run, player, sequence) with a result cache.
- An explicit `weapons.target` and `science.target` in the sim, because scans and XP depend on them. Card rows, pages, tab-bar focus and stick repeat leave the sim.
- The clock: absolute deadline, retained debt, explicit pause, interpolation from completed ticks, and couch focus behaviour preserved.
- Full state including the random-number state published to clients (friends-only, per Net-0).
- Disposal without resetting the shared bitecs index, and a 2,000-cycle plateau test.
- The cross-engine test: Node and real Electron Chromium mandatory; Firefox run when available and reported as NOT RUN otherwise; an AST guard rather than grep.
- Replay v2 with complete init and admitted commands; v1 rejected, with a one-off converter for golden input.
- SIM_VERSION bumped once, one bless, no floor lowered.

## Second review (after Codex applied the amendments)

All five recommendations landed correctly: the rendezvous is gone, the Net-1a/1b split has playable checkpoints, Net-0 is marked approved, and votes, callouts and clock debt are fixed. Codex rightly corrected this review's claim that rows never change mid-console-step. `weapons.ts:134` removes debris and `debris.ts:59` retargets Science inside the console loop; the amended spec handles this with explicit stale-target rejection and differential tracing. That is the correct choice.

Two gaps remained. They are now added as spec amendments 6 and 7:
1. **Incremental migration needed a stated temporary path.** Unmigrated card families keep a single named adapter, deleted family by family and removed in task 11 with a test.
2. **The golden during Net-1a.** It may fail on intermediate commits (the only allowed failure), while every commit passes the projection traces. One bless happens at the end of Net-1a.

One typo was fixed (`T?1` became `T−1`). The spec is ready for the Net-1a implementation plan.
