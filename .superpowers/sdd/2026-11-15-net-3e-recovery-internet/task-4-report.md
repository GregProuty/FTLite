## Changes and interfaces

- `mirrorStore.ts` implements the required `SessionMirror`, `MirrorFileV1`, `MirrorStore`, and `createMirrorStore(directory, validatePayload)` interfaces. Its optional third structural filesystem argument is solely the same failure-injection seam used by `seatStore` (controller approved). The file is `online-mirror-v1.bin`, magic `FTLNMIR1`, a little-endian 32-bit header length, fatal UTF-8/strict bounded JSON header (16 KiB maximum), then exact committed and pending payload lengths. Reads stop after cap+1; file cap is 557,056 bytes, each payload 262,144 bytes, each metadata JSON 4,096 bytes. Strict keys, metadata, SHA-256, origin/room binding and mode validation run before replacement and after reading. Temp files use exclusive creation, owner-only permissions, sync, close, atomic rename, and exact temporary ownership. Reads/writes/clear share one invocation-ordered queue; failed operations do not poison it.
- `validateSectorMirror` belongs to the existing main sector adapter. It uses full checkpoint-v2 validation and verifies run identity, captured tick, layout and complete compatibility against current content. No sector import was added to generic storage, service or mirror coordination.
- `createOnlineMirrors` implements bounded `adopt`, authenticated/coalesced `refresh`, budgeted `flush`, detached `status` and synchronous `dispose`. Initial disk loading and each local-persistence wait have a 1,000 ms budget. An unfinished filesystem operation remains owned by the single serialized worker; only the latest replacement is requested after it. Timeouts produce `persistent:false` / `save-unavailable`. No timeout implies a successful write or releases its ownership.
- Capture bytes are copied before asynchronous work. Metadata hashes the exact owned bytes. Adoption persists pending state before enqueueing upload when storage works, then returns independently of DO commitment. There is one upload and one newest pending replacement; successful older uploads retain the newer pending entry. Flush waiters retain only metadata (maximum 64), never superseded payload history.
- Sequence high water comes from disk and authenticated service state. Rank is `(hostGeneration, checkpointSequence)`, not tick. Conflicting same-rank receipts do not satisfy flush; current pending bytes are resequenced above the authenticated high water. Uncertain PUT results trigger GET and exact metadata/hash/byte validation. A strictly newer validated replacement can satisfy an older flush. An event alone never grants committed status. Disk receipt age starts null and remains null until an authenticated receipt; public status reads calculate current local monotonic receipt age.
- Controller-approved optional `{ signal?: AbortSignal }` arguments were added to `RoomServiceClient.putCheckpoint` and `getCheckpoint`, preserving existing callers. Owner cancellation releases HTTP correlation/deadline/listeners and aborts fetch/body work without closing the authenticated socket. Existing generation/connection fencing remains in force. Cancellation cannot undo a server commit; subsequent GET is the authority for uncertain outcomes.
- `OnlineStatus.mirror` is required and strictly validated. Only metadata, receipt age, pending/persistence booleans and fixed errors cross IPC. Added fixed errors: `save-unavailable`, `save-invalid`, `save-too-large`. Production/fallback status constructors and affected renderer/IPC fixtures include the field.
- Actual app activation exclusively calls `startLeasedHost` with a fresh `randomBytes(16).toString('hex')` utility epoch. The old `OnlinePlatform.startHost` API and app call are removed. Main subscribes to utility renewal requests, uses the exact utility nonce/request identity, aborts superseded service requests, and forwards grants to `applyLease`. The only remaining main lease timer cleans up expired resources; it grants no work permission.
- The capture listener is installed before the start request. Native initial capture is automatic. Main acknowledges bounded adoption, then separately waits for initial DO commitment and the fresh utility grant before `completeBootstrap` and local/remote attachment. The initial explicit Start intent is the sole bootstrap release. This task adds no restore/resume path; the existing utility restore contract stays paused for Task 5.
- Guests refresh through authenticated GET on checkpoint events and active reconnect. Leave/quit requests an exit capture and shares a 3,000 ms commit budget, then releases ownership even after save failure while retaining pending bytes. Native window close waits on the same owner disposal. Forget cancels the context/renewal/mirror epochs first and enqueues both credential and mirror clears before any replacement session can save. Late captures/uploads cannot recreate either file.
- Existing actual-app smoke/runtime/owned cleanup helpers were extended, not replaced. The driver observes the initial utility checkpoint, the public authenticated tick-zero receipt, the subsequent private bootstrap message, the periodic tick-300 notification and matching host/guest committed receipts. Report admission requires these proofs for both layouts and source/artifact hashes for the affected stack. Only fixed diagnostic categories are emitted.
