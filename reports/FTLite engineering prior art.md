# FTLite has no TypeScript twin, so borrow patterns

FTLite sits in a gap: **no open-source TypeScript, ECS-based or web-based FTL-like turned up**, so the stack has no direct prior art, and the nearest engines are GPL or source-available and cannot be copied. The useful material falls into four groups. First, reverse-engineered FTL rules and a Kotlin/GPL co-op fork that prove host-authoritative Commands work for ship state ([Tachyon](https://github.com/sp00nznet/Tachyon)). Second, Barotrauma and Space Station 14 source code that shows how to simulate oxygen, fire and breaches on a room graph ([Gap.cs](https://raw.githubusercontent.com/Regalis11/Barotrauma/master/Barotrauma/BarotraumaShared/SharedSource/Map/Gap.cs), [SS14 atmos](https://raw.githubusercontent.com/space-wizards/space-station-14/master/Content.Server/Atmos/EntitySystems/AtmosphereSystem.Processing.cs)). Third, concrete formulas for skill-scaled output and hazard directors from Barotrauma and Left 4 Dead ([Repairable.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Items/Components/Repairable.cs), [Booth, AIIDE 2009](https://cdn.fastly.steamstatic.com/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf)). Fourth, well-documented determinism, snapshot and replay practice from Gaffer on Games, Factorio and Doom. The headline recommendation is to build a pure fixed-step `step(state, intents)` over bitECS arrays, model hazards as per-room scalars joined by door edges, validate ship JSON with zod, drive stress with a Barotrauma-style asymmetric smoother feeding an L4D-style state machine, and put the same Command/Intent path under couch co-op and later online play. Everything GPL (XFTL, Tachyon, Hyperspace) or source-available (Barotrauma) is read-only reference. Many of the specific tuning numbers and design choices below are inferences from these sources and have not been tested in FTLite, and the final section lists what remains unverified.

## Open-source FTL clones are rare, GPL-bound and off-stack

The only real open-source FTL engine is XFTL / "Project Wormhole" (Kotlin/LWJGL, by ZNix on [GitLab](https://gitlab.com/znixian/xftl)), and its co-op fork **Tachyon** (GPL-2.0-or-later, up to 8 players, created 2026-05-20, last pushed 2026-09-24) adds only UI and multiplayer on top, noting that "all the hard engine work is upstream's" ([Tachyon README](https://github.com/sp00nznet/Tachyon), [GitHub API](https://api.github.com/repos/sp00nznet/Tachyon)). **FTL-Hyperspace** (GPL-3.0, last pushed 2026-11-04, 2,632 commits) is a binary-patching mod framework for the original game rather than a clone, and FTL: Multiverse and Insurrection+ are built on it ([repo](https://github.com/FTL-Hyperspace/FTL-Hyperspace)). The GDQuest Godot tactical space combat demo is **MIT-licensed** but stale (last push 2022) and is a small combat sandbox ([repo API](https://api.github.com/repos/gdquest-demos/godot-2d-tactical-space-combat)). Other GitHub "FTL clone" hits are abandoned or tiny, with no license and 1-7 stars ([search](https://api.github.com/search/repositories?q=FTL+faster+than+light+clone&sort=stars)).

Beyond FTL clones, the closest relatives are Barotrauma (C#, 2,291 stars, pushed 2026-10-27), which has public source but **no open-source license**: the README points to an EULA and shows "Copyright © FakeFish Ltd 2017-2026" ([repo](https://github.com/FakeFishGames/Barotrauma)). Starsector is closed but has community API docs ([CommunityApiDocs](https://github.com/StarsectorCommunityApiDocs/CommunityApiDocs)), and Space Haven (closed) hit v1.0 on 2026-05-13 after about ten years in early access ([MCV](https://mcvuk.com/?p=229763)). Undercrewed, a co-op game in early access, is the nearest commercial relative, though no source was inspected ([Co-Optimus](https://www.co-optimus.com/related-news/undercrewed)). Lovers in a Dangerous Spacetime is the best-documented station-juggling co-op: it runs fully solo with a pet companion filling the second seat, and reviewers say the real strategy is deciding who covers which stations ([Nerdist interview](https://nerdist.com/article/interview-asteroid-base-talks-lovers-in-a-dangerous-spacetime/), [Game Informer](https://gameinformer.com/games/lovers_in_a_dangerous_spacetime/b/xboxone/archive/2015/09/15/lovers-in-a-dangerous-spacetime-game-informer-review)).

Structure worth borrowing is organizational rather than code. Hyperspace separates `src/game/` (mirrors FTL), `src/features/` and `src/overrides/` with tests alongside ([wiki](https://github.com/FTL-Hyperspace/FTL-Hyperspace/wiki/Source-Structure)). Barotrauma splits `BarotraumaClient`, `BarotraumaServer` and `BarotraumaShared`, with `Characters`, `Items`, `Map`, `Events`, `Networking` and `Prefabs` folders ([GitHub API](https://api.github.com/repos/FakeFishGames/Barotrauma/contents/Barotrauma/BarotraumaShared/SharedSource)). The FTLite analogue is a `sim/` package with no Pixi imports, shared by a client and a host. The only multiplayer architecture evidence for FTL-style ship state is Tachyon: every player action is a `Command` executed on the host, clients render streamed snapshots, and doors, crew, power, weapons, events and jumps all sync over TCP ([README](https://github.com/sp00nznet/Tachyon)). Tachyon also avoids shipping copyrighted assets by loading from the user's own game files, which FTLite sidesteps by using original art.

## Rooms-as-nodes beats tile gas for hazards

Two mature codebases bracket the design space. SS14 runs a tile-based gas solver at **15 Hz** with a **3 ms** per-tick budget, an active-tile set, "excited groups" that equalize and then sleep, and an archive-then-share rule so every neighbour reads start-of-cycle values ([CCVars.Atmos.cs](https://raw.githubusercontent.com/space-wizards/space-station-14/master/Content.Shared/CCVar/CCVars.Atmos.cs), [LINDA.cs](https://raw.githubusercontent.com/space-wizards/space-station-14/master/Content.Server/Atmos/EntitySystems/AtmosphereSystem.LINDA.cs)). Its transfer rule divides the delta by `(adjacentTurfs + 1)` as a stability trick, and venting to space multiplies by an escape ratio (0.15) and snaps tiles below a minimum to zero so the sim settles instead of asymptoting ([CCVars](https://raw.githubusercontent.com/space-wizards/space-station-14/master/Content.Shared/CCVar/CCVars.Atmos.cs)). Its Monstermos equalizer has an O(n²) slow path and a fast path that can strand tiles, which is why tile limits of 200 and 2000 exist ([Monstermos.cs](https://raw.githubusercontent.com/space-wizards/space-station-14/master/Content.Server/Atmos/EntitySystems/AtmosphereSystem.Monstermos.cs)). That machinery is overkill for 8-30 rooms.

Barotrauma's hull/gap graph is the better template. Oxygen is a per-hull scalar, a `Gap` connects two hulls (or a hull and outside), and equalization moves each hull toward the volume-weighted mean with a per-step cap, so it cannot overshoot ([Hull.cs](https://raw.githubusercontent.com/Regalis11/Barotrauma/master/Barotrauma/BarotraumaShared/SharedSource/Map/Hull.cs), [Gap.cs](https://raw.githubusercontent.com/Regalis11/Barotrauma/master/Barotrauma/BarotraumaShared/SharedSource/Map/Gap.cs)). A gap's `open` value is continuous 0..1 and scales flow, and zero-flow gaps update every 8th step instead of every step. Fire is capped at 16 sources per hull, grows when oxygen is above 10% and shrinks below, consumes oxygen, and every 5 s each open gap touched by flame has a **15%** chance to ignite the adjacent hull ([FireSource.cs](https://raw.githubusercontent.com/Regalis11/Barotrauma/master/Barotrauma/BarotraumaShared/SharedSource/Map/FireSource.cs)). One flaw to avoid: Barotrauma rolls the spread with `Rand.RandSync.Unsynced`, which would break replay in FTLite, so use a seeded stream instead.

FTL's own numbers come from Tachyon's decompilation-derived docs: oxygen drains 1.2% per second with the system off, an open airlock door loses 16% per second and a hull breach 8% per second, rooms joined by open doors average toward their chunk mean at 8% per second ([doc/oxygen](https://raw.githubusercontent.com/sp00nznet/Tachyon/master/doc/oxygen)). Fires burn out on a random 5-14 counter once oxygen is below 10%, and systems take 8% damage per second from fire ([doc/fires](https://raw.githubusercontent.com/sp00nznet/Tachyon/master/doc/fires)). These are reverse-engineered facts from GPL-licensed notes, so use them as tuning reference only and re-derive FTLite's own table. Simulation timing in FTL is per-second rates multiplied by a speed factor ([doc/reveng-general.md](https://raw.githubusercontent.com/sp00nznet/Tachyon/master/doc/reveng-general.md)), which maps directly onto a fixed step with one `speedFactor` multiplier.

The synthesized recommendation (the notes' own formulation, not a quoted source) is: per room store O2 mass and volume; per edge store conductance (door openness times width); compute `flow = k * conductance * (O2_a/V_a - O2_b/V_b) * dt` from a snapshot, clamped so `k*conductance*dt*(1/V_a+1/V_b) <= 1`; and treat space as a fixed-zero node, so a breach is an edge to space. Tick hazards at 10-15 Hz via an accumulator that carries over lost time, as SS14 does. Test conservation with a vitest property: total O2 plus vented total is constant to epsilon, and no value goes negative or exceeds volume. Add hysteresis between the fire-shrink threshold and the suffocation threshold to prevent flicker.

For ship data, a single versioned JSON per ship is safer than runtime Tiled. Tiled's JSON has pitfalls: GID-to-tileset mapping via `firstgid`, the `type` to `class` rename in 1.9 (partly reverted in 1.10), and infinite maps that store tiles in `chunks` ([Tiled JSON reference](https://doc.mapeditor.org/en/stable/reference/json-map-format/)). The recommended format has `tiles` arrays, a `rooms[]` list (id, volume, system, slots), `edges[]` (a, b or `"space"`, kind, tile, width, defaultOpen) and `stations[]`, validated by zod `superRefine` checks (every roomId exists, each edge lies on the boundary of exactly its two rooms, graph connected, ids unique, array length equals w*h). Validation matters because FTL's own tooling tolerates an unreferenced room ID by creating a stray room in a corner and skewing the ship ([forum](https://subsetgames.com/forum/viewtopic.php?p=33754), a search-snippet source). Keep static layout immutable and dynamic hazard state as flat typed arrays plus a PRNG state, so a snapshot is cheap. Tiled remains optional as an authoring tool converted at build time.

## Skill-scaled stations and directors have ready-to-port formulas

Co-op design evidence converges on one dial: **more simultaneous tasks than hands**. Overcooked's postmortem credits many simultaneous timers and more tasks than players can handle for the intended panic, and notes players repeated solutions until levels forced them out of routine ([Develop post-mortem](https://mcvuk.com/the-develop-post-mortem-overcooked/)). Keep Talking and Nobody Explodes used asymmetric information and a hidden system that fires disruptions when the defuser does well, and lost players to ambiguous rules that players rarely reported ([Game Developer](https://gamedeveloper.com/design/finding-the-fun-in-bomb-defusal-with-i-keep-talking-and-nobody-explodes-i-)). Quarterbacking remedies are hidden information, real-time pressure and role differentiation, though sources disagree whether it is a design or a people problem ([Mitigating quarterbacking](https://donteatthemeeples.substack.com/p/mitigating-quarterbacking-cooperative-games), [Erik Twice](https://eriktwice.com/en/2021/03/12/alpha-player-cooperative-games-symptom/)). For FTLite, walking between rooms is itself the anti-quarterback device, so the recommendation is to scale hazard concurrency (not strength) with player count and to give solo play a lower cap and a slower director. L4D fills absent humans with bots that prioritize human teammates ([Booth](https://cdn.fastly.steamstatic.com/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf)), and Lovers uses a companion, supporting a weak automatic drone that mans one idle station.

Barotrauma's source supplies the skill math. Gain is `min(baseGain / max(level,15)^1.5, 2)`, with the code's own comment that the formula is too generous at low levels, hence the divider floor ([CharacterInfo.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Characters/CharacterInfo.cs)). Defaults include 0.005 skill per second steering, 0.001 per second on a turret, and 0.5 per CPR revive ([SkillSettings.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Characters/SkillSettings.cs)). Repair duration is `lerp(100, 10, successFactor)` seconds with `successFactor = ((skill - required) + 100)/2/100` ([Repairable.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Items/Components/Repairable.cs)). The inference for FTLite is a `lerp(slow, fast, (level+100)/200)` output mapping so an unskilled operator still runs at about half of max, which helps new and solo players. At 0.001-0.005 per second, a level takes hundreds of seconds at mid skill, so tune constants so a 20-minute session moves a player a few levels.

For the director, two sources compose cleanly. L4D keeps one intensity float per survivor that rises with damage and incapacitation, decays over time, and does not decay while enemies are engaged. A four-state cycle runs Build Up, Sustain Peak (3-5 s), Peak Fade and Relax (30-45 s), and the design principle is that the algorithm "adjusts pacing, not difficulty" ([Booth](https://cdn.fastly.steamstatic.com/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf), [GDC 2009](https://cdn.fastly.steamstatic.com/apps/valve/2009/GDC2009_ReplayableCooperativeGameDesign_Left4Dead.pdf)). Barotrauma's `EventManager` recomputes intensity every 5 s from crew vitality, hull breaches, fire, flooding and enemies; smooths asymmetrically (rise 0.04/s, fall 0.0025/s, so it lingers about 400 s); lets an event start only if intensity is at or below a threshold that starts at 0.2 and rises toward 1.0; and seeds an `MTRandom` while down-weighting recently used events by ×0.1 over a 20-event history ([EventManager.cs](https://github.com/FakeFishGames/Barotrauma/blob/master/Barotrauma/BarotraumaShared/SharedSource/Events/EventManager.cs), read through a fetch-tool summary, so verify the file). The proposed FTLite director: one `stress` float from hazard state with fast-up/slow-down smoothing, the L4D state machine over it, a rising threshold so spawns eventually resume, and spawn budgets scaled with player count (the `base * (0.6 + 0.4*N)` figure is an unsourced suggestion). Run the director on its own seeded stream, separate from cosmetic RNG, and do not let stress decay while a hazard is unattended. For downed players, the notes found only weak evidence and recommend a short downed time with a hold-to-revive speed-up, a pure design judgement ([Game Developer: revive mechanics](https://www.gamedeveloper.com/design/co-op-revive-mechanics)).

## Determinism, intents and replay tests form one pipeline

The simulation core should be `step(state, inputsPerPlayer) -> state` with serializable state. Fixed-step with an accumulator is the standard pattern: cap frame time at 0.25 s, step at fixed dt, and render with `alpha = accumulator / dt` ([Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)). Intents are the only sim input, which is exactly what lockstep sends: six booleans fit in about 6 bits per frame, so bandwidth is independent of object count ([Deterministic Lockstep](https://gafferongames.com/post/deterministic_lockstep/)). For FTLite's slow pace, the recommended path is host-authoritative: clients send intents with a target tick, the host steps and broadcasts snapshots (about 5 Hz, optionally delta-compressed against an acknowledged baseline) plus a hash, and snapshots forgive float drift and give late-join for free ([Snapshot Compression](https://gafferongames.com/post/snapshot_compression/)). This matches Tachyon's model. Lockstep needs bit determinism (Age of Empires reportedly found identical results across machines hard, per a secondary source ([Game Developer](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond))), and Factorio pairs lockstep with per-tick CRCs and resync on desync ([FFF-55](https://factorio.com/blog/post/fff-55)). Rollback (GGPO/GGRS) requires whole-state save/load/advance and optional checksums ([GGRS](https://docs.rs/ggrs/latest/ggrs/)). It is a later luxury, not day one.

Library adoption is not recommended. netplayjs offers rollback and lockstep wrappers with JSON-serializable state but has its own loop and fixed canvas assumptions, with unclear maintenance (251 commits, 576 stars, no last-commit date seen) ([netplayjs](https://github.com/rameshvarun/netplayjs)). Colyseus Schema is delta-encoded but would duplicate bitECS state and caps classes at about 64 fields ([README](https://cdn.jsdelivr.net/npm/@colyseus/schema@4.0.28/README.md)). The alternative is a thin `Transport` interface over a WebSocket server in Electron's main process, Trystero WebRTC ([README](https://unpkg.com/trystero@0.21.6/README.md)), or Steam Networking Sockets (Valve deprecates legacy ISteamNetworking, per [Steamworks docs](https://partner.steamgames.com/doc/api/ISteamNetworking)).

JavaScript determinism rules: basic arithmetic is IEEE-754 reproducible, but transcendental `Math` functions vary by implementation, so avoid `sin/cos/atan2/pow` in the sim or patch them ([Rune](https://developers.rune.ai/blog/making-js-deterministic-for-fun-and-glory/), [Rapier](https://rapier.rs/docs/user_guides/javascript/determinism)). Rune replaces `Math.random` with a seeded mulberry32 whose state is tracked for rollback, patches `Array.sort` with a defined comparator, and ships an ESLint plugin to flag globals. For FTLite: mulberry32 with named sub-streams (combat, loot, events, director) held in state; no `Date`, `performance.now` or `Math.random` in `sim/`, enforced by lint; sorted entity IDs wherever iteration order affects RNG draws or damage (an inference, since bitECS 0.4 query ordering is unverified); stable cross-wire IDs rather than raw eids.

bitECS 0.4 ships `bitecs/serialization` with SoA, AoS, Observer and Snapshot serializers, with `diff`, a 100 MB default `buffer` (set a smaller one) and `epsilon` options, and entity-id maps ([Serialization.md](https://raw.githubusercontent.com/NateTheGreatt/bitECS/main/docs/Serialization.md), [0.4.0 docs](https://cdn.jsdelivr.net/npm/bitecs@0.4.0/docs/Serialization.md)). There is no versioning support, so prefix every snapshot with `{formatVersion, simVersion, tick, rngState}` and a component manifest. Do not hash through the epsilon diff path; hash raw typed-array bytes (FNV/xxhash) instead, available every tick from day one.

Replay testing follows Doom and Factorio practice: record `{version, seed, config, per-tick intents}`, replay headless, and compare hashes ([Doom Wiki: Demo](https://doomwiki.org/wiki/Demo), [Headless Doom](https://olafurw.github.io/2022-12-04-headless-doom/), [FFF-188](https://factorio.com/blog/post/fff-188)). In vitest, checks are golden replays comparing the final hash plus mid-run hashes every 60 ticks to localize failures with a "bless" script, plus fast-check properties: same seed and intents give the same hash, save at tick N then load then continue equals the uninterrupted run, intent streams split across different render-frame sizes give identical results, fuzzed intents never produce NaN or out-of-range values, and snapshot round-trip is identity. fast-check's model-based testing prints seed, path and replayPath for exact reproduction ([docs](https://fast-check.dev/docs/advanced/model-based-testing/)). Do not over-engineer: skip rollback, custom bit-packing, interest management, NAT traversal and fixed-point math everywhere until playtests demand them.

## Stack specifics: bitECS 0.4, PixiJS v8, collision, gamepads, Electron

**bitECS 0.4.** Components are plain objects of SoA typed arrays or plain arrays, with `createWorld`, `query(world, [Position, Or(Health, Shield), Not(Stunned)])`, observers (`onAdd`, `onRemove`, `onSet`), relations and entity indexes with optional versioning ([Intro.md](https://github.com/NateTheGreatt/bitECS/blob/main/docs/Intro.md), [README](https://cdn.jsdelivr.net/npm/bitecs@0.4.0/README.md)). AoS arrays are the documented way to hold strings. Removed ids are recycled immediately by default, and the docs recommend tagging entities and removing them in a batch. So the renderer must not hold eids across ticks without a liveness check or versioned ids. The inferred layout: `sim/` exports world and stores and never imports pixi; the renderer observes a `Renderable` tag to create and destroy sprites and keeps `prevX/prevY` for interpolation; room adjacency lives in a side table or an `AdjacentTo` relation and is rebuilt from ship data on load, since snapshots would not restore such tables. No open-source bitECS 0.4 plus PixiJS game surfaced; only a Phaser 3 + bitECS tutorial and one Phaser example skill ([ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fourcade%2Fphaser3-bitecs-getting-started), [skills.sh](https://www.skills.sh/kadajett/sdr/example-game)).

**PixiJS v8 tile maps.** Initialization is async (`await app.init()`), culling is no longer automatic, scale modes are strings like `'nearest'`, and the ticker callback receives the `Ticker` ([v8 migration guide](https://pixijs.com/8.x/guides/migrations/v8)). `@pixi/tilemap` 5.x (the README's version table maps it to Pixi v8, though the fetched table was garbled) provides `CompositeTilemap`, which layers tilemaps to hide texture limits, with 16k tiles per tilemap by default ([repo](https://github.com/pixijs-userland/tilemap)). Render Groups (`isRenderGroup: true`) suit separating world from HUD ([guide](https://pixijs.com/8.x/guides/concepts/render-groups)). For a small static ship, one `CompositeTilemap` per ship inside a world render group, rebuilt only on tile change, should suffice, and culling is likely unnecessary. Integer scaling (`floor(min(w/W, h/H))` with nearest filtering) and per-room overlay sprites tinted from sim values are standard but unsourced.

**Tile collision and pathfinding.** Move per axis against solid tiles, Celeste/TowerFall style, which gives wall sliding and determinism for free. The source article could not be fetched ([Thorson](https://maddythorson.medium.com/celeste-and-towerfall-physics-d24bd2ae0fc5)), so treat the per-axis integer-pixel-with-remainder details as unverified recall. Doors are tiles whose solidity is a function of door state behind a `solid(tx, ty)` query. Normalize and clamp analog input so diagonals are not faster. For AI and unattended-station logic, Red Blob Games covers BFS flow fields, Dijkstra and A* ([intro](https://www.redblobgames.com/pathfinding/a-star/introduction.html)). The GDQuest demo's author hit unsolved problems with continuous navigation: a NavigationPolygon bug, grid fire spread that was "not fun", and door timing with several units ([NOTES.md](https://raw.githubusercontent.com/gdquest-demos/godot-2d-tactical-space-combat/master/NOTES.md)). Space Haven players report crew drifting into space from a pathfinding bug ([Steam thread](https://steamcommunity.com/app/979110/discussions/0/2790494800095171444)). The lesson is to use a tile grid with room tags and doors as explicit edges with one-at-a-time occupancy, and to give any NPC priority table an explicit tiebreak. FTL's crew AI locks up at priority 100 when every room is rated dangerous ([doc/crew-ai](https://raw.githubusercontent.com/sp00nznet/Tachyon/master/doc/crew-ai)).

**Gamepads in Electron.** Poll `navigator.getGamepads()` every tick as the source of truth, tolerate null entries, treat `index` as ephemeral (indices can be reused after disconnect) and do not parse the `id` string; `gamepadconnected` fires for already-connected pads only after a button press or axis move ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Gamepad_API/Using_the_Gamepad_API)). An older devlog also reports unreliable connect events in Chrome ([itch.io devlog](https://theedgeofthought.itch.io/eelemental/devlog/797/chrome-has-no-gamepadconnected-event)). The design inference: a `DeviceManager` assigns devices to press-to-join `PlayerId` slots, marks disconnects as awaiting rebind with neutral input, uses any-press-to-reclaim on reconnect (identical pads share ids), treats keyboard clusters as virtual devices, applies a radial deadzone of roughly 0.15-0.25 (conventional, unsourced), and feeds the sim a per-tick `InputFrame` per `PlayerId`, which makes headless tests and replays trivial.

**Electron and vitest.** Chromium switches go through `app.commandLine.appendSwitch` before `ready` ([docs](https://www.electronjs.org/docs/latest/api/command-line-switches)). Steam integration should use steamworks.js rather than Greenworks, which is in best-effort maintenance, with the overlay enabled at the end of `main.js` ([steamworks.js](https://awesome.ecosyste.ms/projects/github.com%2Fceifa%2Fsteamworks.js), secondary). The fixed accumulator makes frame-limit flags probably unnecessary. For vitest, nothing was sourced: the research did not review vitest or ECS testing material, so the harness recommendation above (scripted `InputFrame` sequences, golden hashes, fast-check properties) rests on the architecture, not on prior art.

## License cautions

Do not copy code from XFTL, Tachyon (GPL-2.0-or-later) or Hyperspace (GPL-3.0): any copied GPL code would force FTLite itself under GPL ([Tachyon](https://github.com/sp00nznet/Tachyon), [Hyperspace](https://github.com/FTL-Hyperspace/FTL-Hyperspace)). Barotrauma and its Lua modding docs are source-available under an EULA with a FakeFish copyright, so it is fine to read and learn from but not to copy ([repo](https://github.com/FakeFishGames/Barotrauma)). Reimplement the formulas here from the ideas, with your own constants, and treat the Tachyon decompilation tables as reference, not as a data file to import; the notes suggest checking with a lawyer if exact reverse-engineered tables matter. The GDQuest demo is MIT and safe to reuse, but it is a small stale sandbox. SS14 and RobustToolbox are believed to be MIT, but this was not verified in the research, so read the LICENSE files before reusing anything. Use original art and audio only, as Tachyon's approach of loading retail assets is not available to a distributable game. Libraries to adopt (bitECS, PixiJS, `@pixi/tilemap`, zod, fast-check, seedrandom or Prando) need their own license check before shipping; this was not done.

## Gaps and unverified claims carried over from the notes

**Source access failures.** The FTL fandom wiki returned HTTP 402 and the Barotrauma wiki and several others returned 401/403, so FTL numbers beyond Tachyon's docs come only from search snippets or player posts: door fire-slowdown multipliers (1.75x closed, 10x blast), the heavy laser 30%/30% fire-then-breach roll, and "fires die only when oxygen is fully drained" are all unverified. FTL's skill XP values conflict between sources and are unverified. The primary FTL layout grammar (`.txt`/`.xml`) was never fetched: the room/door/station-slot description (tiles 35 px, slots numbered 0-3, a conflicting door-orientation flag) comes from forum search snippets, as does the stray-room failure mode. No FTL events or sector XML schema was read. The Tachyon `doc/` numbers are decompilation-derived by the author and not cross-checked against the game.

**Not fetched or not researched.** XFTL's own license, last commit and data model (GitLab not opened). SS13 original LINDA/Monstermos code (only SS14's port), SS14's gas reaction (`React`) code, SS14 map YAML (404), Oxygen Not Included internals, power-network prior art (the graph-component suggestion is first-principles only), and Space Haven, RimWorld and Dwarf Fortress internals. ## Conclusion

The research shifts the question from "what can we reuse" to "what can we trust". Only the generic engineering layer (fixed step, intents, hashed snapshots, golden replays) has strong, directly sourced, license-clean prior art, and it also happens to be the layer that makes couch co-op and later networking the same code path. The game-specific layer (hazards, skills, directors) rests on two readable but non-copyable codebases and one decompilation, so FTLite must write original implementations and tune them by playtest, with the formulas above as starting points rather than answers.

The cheapest high-value next steps are to build the headless harness first (pure `step`, `InputFrame` per `PlayerId`, `hashState`, a golden replay in vitest), then prototype the room-graph oxygen/fire model with the conservation property test, and only then spend effort on the director. Resolving a few gaps early would remove the largest risks: a small bitECS 0.4 spike to confirm snapshot and query-order behavior, a real-controller test in a built Electron app, and a LICENSE check of any library or reference you plan to adopt.
