# Codex review: 4-ii spec half 1 (2026-11-10)

1. **High — Spec lines 42–47, 97: first-down/death names cannot be reconstructed.** The HUD requires `First down: Okoro 3:10`, but telemetry retains only timestamps. After revives or subsequent casualties, current life states cannot identify the first casualty. **Fix:** store `firstDownPid` and `firstDeathPid` alongside their ticks; define simultaneous-event tie-breaking and include both IDs in flatten/unflatten, snapshots, and hashes.

2. **High — Spec lines 7, 101: the unchanged bot cannot exercise station choices.** `tests/helpers/bot.ts:59` only moves, repairs, and revives; it never sends Confirm or operates consoles. Consequently every station remains never manned and shots/hits remain zero. These runs cannot answer the foundation’s useful-station-choice or task-clarity acceptance questions (§10). **Fix:** describe these runs as automated telemetry soaks and retain the human acceptance playtest; add station-operating bot behavior if automated station coverage is required.

3. **Medium — Spec lines 16, 66: contradictory activity classification after incapacitation.** A player can add repair/revive progress in `interactSystem`, then become Downed in debris or crew processing. The scratch flag makes that tick active under line 66, whereas line 16 says Downed and Dead ticks are idle. **Fix:** explicitly choose whether activity earlier in the tick takes precedence over final life state, and give the mixed-case rule. Set revive activity only for the arbitrated reviver, including the completion tick before `reviveCrew` resets progress.

4. **Medium — Spec lines 63–67: final-state sampling can discard activity on the ending tick.** Weapons and Navigation can act before `downCrew` clears seating and `shedPower` changes station availability. The final telemetry pass then records no manning and may record idle despite an actual shot or evasion roll. **Fix:** explicitly define these counters as final-state samples, or capture station activity at its observation point before those mutations. Specify expected results for a seated operator downed on the ending tick and require later `step()` calls to leave counters unchanged.

5. **Medium — Spec lines 67, 91, 95: event timestamps lack an elapsed-time convention.** Current `step.ts:50` increments `state.tick` after system processing. Thus an event stored as tick `t` is reported against a completed duration of `t + 1` ticks. **Fix:** specify whether first-event times denote the start or completion of the event tick, place telemetry explicitly before `state.tick++`, and define conversion accordingly. Cover an event during tick zero and during the ending tick.

6. **Medium — Spec line 70: the shot increment point needs an explicit guard.** `fireWeapon()` returns `false` for both a fired miss and a rejected attempt (`weapons.ts:35–51`). Counting successful returns loses misses; counting calls includes invalid attempts. **Fix:** increment `shots` once after either weapon branch passes readiness checks and consumes readiness, beside `lastShotTick`; increment `hits` only inside the hit branch before debris removal.

7. **Medium — Spec line 96: malformed stored data has no recovery rule.** Swallowing failures around read/parse/append/write leaves malformed JSON or a valid non-array value permanently preventing subsequent records from being saved. **Fix:** treat parse failures and non-array roots as an empty history, append the current record, then retain the newest 50. Separately swallow storage-access/write failures; specify checks for malformed data and the 50-to-51-record boundary.
