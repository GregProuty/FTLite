1. **High — §4 contradicts binding parent §7.** The proposed `Container` of tile sprites replaces the parent’s required `CompositeTilemap`. Explicitly amend the parent or retain that architecture; the current Graphics implementation does not waive the requirement. [Art §4](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:67), [parent §7](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-09-foundation-design.md:231).

2. **High — §§3–4 lack a usable asset lookup contract.** `texture(name)` has no corresponding manifest field for named static frames. Floors, wall variants, UI panels, glyphs and eight directional crew animations have no defined names or bindings; duplicate animation names and missing required names can pass the specified tests. Animation speed, looping and 9-slice borders are also unspecified. Pack replacement cannot reliably be “manifest only.” [§3](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:57).

3. **High — §§3, 6–8 omit asset delivery in built applications.** Root `assets/` has no configured serving/copy mechanism, the loader has no defined manifest URL, and packaging includes only `out/**/*`. The generated notices likewise have no shipping step. A development-only gate cannot establish that art or attribution reaches the installed build. [§6](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:90), [Vite config](C:/Users/djuar/FTLite/electron.vite.config.ts:3), [packaging](C:/Users/djuar/FTLite/electron-builder.yml:6).

4. **High — §§3, 6–7 give incompatible missing-file rules.** Every manifested file must exist, yet missing in-house files must only warn. Omitting those entries instead loses their bindings and leaves the loader’s “planned files” inventory undefined. §7 also makes failed PNG loads recoverable while requiring absent third-party packs to stop startup. Define required/optional entries and distinguish missing, corrupt and unmanifested files. [§6](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:91), [§7](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:98).

5. **High — §§3, 5 erase the crew export’s provenance.** `body_base.png` is explicitly a recoloured Shade asset, but all `art/` files must identify only the owner, `source: assets/art`, and `license: original`. CC0 permits editing; it does not make that an accurate provenance record under parent §12. Record Shade, the original source/licence and the recolour modification. [§5](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:76), [parent §12](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-09-foundation-design.md:308).

6. **Medium — §§2, 5, 9 leave known geometry decisions unresolved.** The research identifies Puny’s **32×32 canvas** and Cozy’s **16×32 front walls**, whereas the brief says all pieces are 16 px. No pivot, footprint, cropping or wall overlap rule connects these sprites to the renderer’s crew-centre coordinates and square tiles. These choices affect rendering structure, so §9’s claim that inspection changes only frame tables is unsupported. Resolve them before committing one implementation plan. [§5](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:76), [research](<C:/Users/djuar/FTLite/research/Open art assets for FTLite.md:9>).

7. **Medium — §4 cannot label the existing HUD prompts correctly.** `HudPlayer.prompt` combines Interact and Confirm into one string, but the spec supplies one glyph using E/Enter. Confirm actually uses F/Right Shift, and gamepad Interact/Confirm use different buttons. Define action-specific prompt entries and mappings, including empty/reconnecting slots whose key is `null`. The proposed device derivation in `session.ts` also contradicts §4’s “Cancel binding only” exception. [§4](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:70), [HUD](C:/Users/djuar/FTLite/src/renderer/src/render/hud.ts:15), [bindings](C:/Users/djuar/FTLite/src/renderer/src/input/sources.ts:14).

8. **Medium — §4 persistent damage has no run reset.** One renderer survives restarts; crew caches use StableIds without a run identifier. Damage “keyed by tile index” would survive into the next run unless explicitly cleared, and facing/interpolation history can also persist. Define run-boundary reset behavior and test consecutive runs through the same renderer. [§4](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:68), [session start](C:/Users/djuar/FTLite/src/renderer/src/app/session.ts:39).

9. **Medium — §4’s door animation state machine is incomplete.** It omits Sealed→Closed, initial state, interrupted/reversed playback and transitions skipped between rendered frames. The actual sim supports sealing/unsealing and advances multiple ticks per draw. Specify final-state reconciliation and test transitions as pure logic; sheet slicing tests cannot catch a door visually stuck sealed or open. [§4](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:67), [door logic](C:/Users/djuar/FTLite/src/renderer/src/sim/doors.ts:33).

10. **Medium — §4’s breach damage targets the wrong kind of tile.** Valid breach sites are wall tiles, while damaged-floor art must overlay floor tiles. The spec never identifies which adjacent floor tiles become damaged, nor how vent direction is derived. Implementers must invent that mapping. [§4–5](C:/Users/djuar/FTLite/docs/superpowers/specs/2026-11-10-art-pass-design.md:68), [ship validation](C:/Users/djuar/FTLite/src/renderer/src/sim/ship/schema.ts:80).

11. **Medium — §§4, 6 leave credits behavior untestable as specified.** No scroll control, credits visibility contract, Confirm/Join behavior while open, or simultaneous Confirm/Cancel priority is defined. Before anyone joins, `DeviceManager` supplies no active player Cancel events, so opening credits from the initial lobby also needs an explicit input policy. Add session tests for these behaviors.
